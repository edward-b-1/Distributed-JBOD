Object health in the web UI

How the console could say how many objects the cluster holds and whether each can be read, drawn in the console's own colours, light and dark side by side. Every mock uses the demo cluster as it stands today.

  • scheme 2+1, three shards per object, any two suffice
  • 245,756 versions stored
  • devbox4 unreachable, its devices demo-d1 and demo-d2 unavailable
  • every object has two shards on devbox4, so every GET fails right now

1. The card on the Overview

Three treatments of the same numbers, each sitting under the cluster health card that already exists. The counts come from a records-only scan, so the card is refreshed on demand and says when it was last computed, rather than on every page refresh.

Same shape as the cluster card: one mark, one line, one sub-line, and an action on the right. The completeness statement is the sub-line's last clause.

5. Where the numbers come from

Sections 1 to 3 need one node-side operation; section 4 needs none.

PieceSourceCostNeeds
Card countsA records-only merge of every reachable device's record stream, as the scrub's cross-node phase does since #162, counting shards on available devices per version instead of checking themone record scan per device, minutes at 245k versions; on demandnode and client work, a SPEC section
Completeness lineWhether any unreachable node lists at least k+m devicesfree, from the documentthe same operation
Health filter and Shards columnThe summary's per-key results, or one HEAD per listed key until then100 small calls per page if lazyUI only, better with the operation
Record view verdictThe record's shard devices against the status's availabilitynoneUI only

Recommendation. Do section 4 now as a UI PR; it answers "can this object be read" today. Ask the node owner for the summary operation, with the four states of section 2 as its contract and the completeness rule in it. Then add the card as treatment A, since it sits beside the cluster health card as its equal and the two together answer "is the cluster healthy" and "is the data healthy" in one glance, and the Shards column and health filter on the Objects page.

Treatment B earns its place only once counts are mixed, which they will be during a drain; it could replace A's sub-line later. Treatment C is the least work but hides the completeness statement, which is the one line that must not be missed.
